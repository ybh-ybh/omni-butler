# 后端业务接口与解耦审计（精简方案）

复审日期：2026-10-20。代码基线：82e48e7。范围：名人名言、24 小时时间记录、待办、物品、会员、事件、笔记。

本方案按“如无必要，勿增实体”组织改造，目标是让应用内对话助手通过 tool_call 操作业务，让 Codex 通过 MCP 操作同一批业务，并完成周/月总结。

实现进度（2026-10-20）：按用户确认的本轮范围，已新增七模块后端可复用方法、范围统计和测试，由 BusinessModule 导出。调用契约及发布边界见[业务接口说明](D:/codeRepertory/MyCodeRepertory/omni-butler/apps/server/src/business/README.md)。应用内聊天界面、Function Calling 和 MCP 协议入口留待后续接入；以下现状与缺口清单记录的是 82e48e7 审计基线，实施结果以该接口说明和测试证据为准。

## 1. 修订结论

**保留现有架构，补齐真正缺失的服务端业务方法，让两个工具入口共用。** 不再把七模块整体分层、同步框架重写或笔记/AI 服务拆分作为接入前提。

审计基线中，前六个业务主要由 Flutter Repository 执行业务规则，再通过 POST /sync/operations 同步；笔记专用接口主要处理音频、ASR 和整理任务，正式正文 CRUD 也缺少完整的服务端调用入口。本轮据此补齐业务方法，继续复用已有服务和规则。

采用三个判断标准：

- 已有服务方法能正确完成操作，就直接复用。
- 缺少业务行为，才新增方法；出现实际重复或明确的测试/运行边界，才抽函数或拆文件。
- 新表、新接口、版本字段、后台任务必须解决已选能力的具体问题，不能只因“未来可能用到”而提前建设。

| 原方案中的要求 | 本次处理 | 最小替代及理由 |
|---|---|---|
| 每模块预建 Commands、Queries 和多个 Policy 类 | 删除固定拆分类表 | 同模块读写可以放一个普通服务；复杂计算按需用纯函数，不按职责名机械建类 |
| 另建 SyncBatchAdapter、TransactionExecutor、持久化抽象层 | 删除 | 保留 SyncService、Prisma 和现有事务；只有重复的锁/校验代码需要复用时才提取小函数 |
| 为工具先补七套独立 REST Controller | 不作为要求 | 同进程两种工具入口直接调用业务方法；只有真实 HTTP 调用方需要时才增加路由 |
| 拆 NotesService、AiService、ImagesService、全部 worker | 从实施路线删除 | 现有服务有可用边界；普通数据 CRUD 不依赖这轮内部整理 |
| 预建 NoteAudioStorageModule、ResponsesClient、提示词/预设分层 | 延后到实际需要 | 独立运行存储/worker，或聊天确需共用网络代码时再局部提取 |
| 为 SQL 白名单、快照和 DTO 建统一定义/生成机制 | 删除 | 保留现有协议；新增方法显式校验必要字段，仅合并确实相同的常量 |
| 所有写操作统一回执、revision、冲突候选 | 改为按操作需要 | 非幂等副作用持久去重；复用已有版本/回执。普通记录不预建候选表 |
| 所有 GET/本机 watch 都先改成纯查询 | 删除全面改造要求 | 新工具的只读声明必须真实；需要纯查询时直接读取已有数据，不重写本机初始化流程 |
| 先改完七模块，再拆资产系统，最后接两种工具 | 改为逐模块交付 | 一个业务方法完成后即可同时适配两入口，随后覆盖其余业务 |
| 先建统一统计/总结平台、全部列表游标 | 删除提前建设 | 复用有界查询和确定性统计；需要遍历时才加分页，周/月只是日期范围参数 |

这不要求清理全部 82 个仓储方法，也不要求把它们一一变成模型工具。附录保留完整事实清单，便于需要某项能力时找到已有实现。

## 2. 为两种入口留下的最小扩展点

~~~mermaid
flowchart LR
  CHAT[应用内聊天：模型提出 tool_call] --> FC[Function Calling 入口]
  CODEX[Codex] --> MCP[MCP 入口]
  FC --> BIZ[同一批业务方法]
  MCP --> BIZ
  BIZ --> DATA[现有 Prisma、事务及业务表]
  SYNC[现有 SyncService] --> DATA
~~~

图中表示调用关系，不要求新增同名类、抽象基类或框架。初期一个静态的“工具名称 → 参数定义 → 业务方法”映射即可；两种协议只做必要的格式转换。

每个新增业务方法负责运行时参数校验、可信归属、当前记录检查及事务。不能只依赖现有 HTTP ValidationPipe，因为同进程工具调用不会自动经过 Controller。模型不决定 owner/userId，也不接收任意表名、SQL、对象存储 key 或部署密钥。

**应用内对话助手。** 开发聊天功能时，增加“发送消息 → 接收工具调用 → 校验并执行 → 回传工具结果 → 生成回复”的编排，设置有限的调用轮数并支持取消。业务结果提供实体 ID、实际变化、冲突或候选信息，聊天界面据此显示确认/编辑卡片。确认应绑定具体参数和目标，确认后的执行仍检查最新状态。

当前 AiProvider 只处理纯文本 Responses 输出，并不是现成的工具循环。届时按实际需求扩展聊天调用，复用可用的配置、密钥保护、网络限制和错误处理；不把工具执行塞进笔记整理流程，也不提前换 Agent 框架。供应商/模型是否支持所需工具协议，在实现聊天调用时验证。

会话历史和短期上下文属于聊天功能；开始实现持久会话时再定义必要存储。业务方法不依赖对话内容、记忆数据库或提示词，后续长期记忆因此可以独立添加；现在不预建向量库、记忆服务或通用会话框架。

**Codex MCP。** MCP 工具调用同样的业务方法、参数规则和结果，不再复制一套增删改查；也不需要先经过应用内模型。连接鉴权要在实际 MCP 接入时完成，将获授权身份转换为现有业务归属检查，不让模型自报身份。具体传输和凭据方式按部署环境选择，本轮不引入新的用户/角色系统。

应用与 MCP 均能逐步获得七模块 CRUD 和统计能力。数据提交到现有业务表后继续经 PowerSync 下发；工具成功以服务器实际提交为准，本机尚未同步的数据不能被描述为已经纳入统计。

## 3. 七模块实际需要补什么

默认“删除”沿用移入回收站。永久删除、全库替换、批量未来范围等单独表达，不能藏在普通 update 中。简单字段编辑用一个受限 update 方法即可；只有业务含义不同、会连带改动多条记录的动作才单独提供方法。

| 业务 | 两入口共用的基本能力 | 确有必要的业务动作及规则 | 总结/分析所需数据 |
|---|---|---|---|
| 名人名言 | 列表/详情、新增、编辑、软删除；启停可纳入受限编辑 | 日签轮换按需要新增；沿用稳定日期槽位及删除引用规则。JSON 导入导出继续留原流程，不列首批工具 | 日期对应日签或筛选后的名言；不额外建统计模块 |
| 时间记录 | 范围查询、新增完成记录、编辑、软删除 | 开始/结束记录单独处理；校验区间、进行中及重叠，保留多设备冲突记录可收尾的现有通路 | 裁剪范围后按日/分类求时长，进行中使用固定截止时间 |
| 待办 | 详情/列表、新增、编辑、软删除 | 完成/重开处理父子联动；进度步骤与最终确认分开；未来系列修改明确范围。普通字段仍可共用 update | 计划日与完成日分别统计，返回未完成任务及步骤状态 |
| 物品 | 搜索/详情、新增、编辑、软删除；状态可纳入受限编辑 | 配件父子与分类位置引用检查；批量搬家保留独立操作和跟随配件规则 | 分类/位置/状态、数量/金额；明确是否包括配件，避免重复计价 |
| 会员 | 详情/列表、新增、编辑、软删除 | 记账/撤销账目必须同时维护到期信息；已有稳定自动账期规则继续使用，暂不迁移自动补账调度 | 按账目业务自然日计支出、到期分布；金额用整数分值 |
| 事件 | 活动/归档/历史查询、新增、编辑、软删除 | 记录完成/撤销及历史编辑后重算最近完成时间；归档可纳入受限编辑；category 继续是自由文本 | 有效完成历史、应做时间、逾期情况；月/年周期保持日历算法 |
| 笔记 | 列表/详情/搜索、新增、编辑、追加、软删除；置顶/记录时间/标签沿用现有含义 | 正文写入建立不可变版本并检查基线；冲突保留现有候选机制。复用已有附件/原音接口 | 正式正文、有效标签、原始转写及记录自然日统计；排除本机未提交草稿 |

服务端已有部分可复用规则：[sync-consistency.ts](D:/codeRepertory/MyCodeRepertory/omni-butler/apps/server/src/sync/sync-consistency.ts:109) 维护待办和事件最终状态，[note-sync.ts](D:/codeRepertory/MyCodeRepertory/omni-butler/apps/server/src/sync/note-sync.ts:99) 维护笔记修订。先调用或局部提取已有函数，不先改造成新的规则体系。

新增查询使用明确的筛选、稳定顺序、数量上限，并说明是否截断。若需要完整遍历再增加分页；总结不能把截断列表当完整数据集求合计。

周总结和月总结使用同一组范围查询/统计：明确起止日期、业务时区、截止时间和口径，由代码算时长、金额、数量，模型负责组织文字。返回计数及必要的记录 ID，正文按需选取；不要求一次把全部原文发送给模型，也不需要新建周总结/月总结实体或表。用户要保存总结时，直接调用普通笔记新增方法。

## 4. 精简后仍不可省的正确性

### 4.1 业务行为和事务

会员记账与到期推进、事件历史与最近完成值、待办父子状态、笔记正文与版本必须原子一致。不能让模型连续发多个底层写表操作来模拟一次业务动作。

在线方法生成所需变更，离线同步继续上传已经生成的本地变更。双方只共用适用的校验和派生计算；不能将每条 PATCH 反推为“续费”或“完成”，否则会重复产生支付/历史。

[SyncService.applyBatch](D:/codeRepertory/MyCodeRepertory/omni-butler/apps/server/src/sync/sync.service.ts:65) 已承担批次事务、owner 锁、原始负载摘要、回执和墓碑。保留这些实现；需要聚合完整性的校验放在批次最终状态，不因中间步骤暂不完整而拒绝合法事务。

### 4.2 重试与并发分别处理

创建记录、追加正文、会员记账、记录事件完成、计费任务等，响应丢失后的重试不能重复产生副作用。优先复用已有任务回执、稳定业务身份和唯一约束；执行层保持同一次操作身份，不能每次重试换 ID。若现有存储不能校验同身份同内容或恢复实际结果，才为该需求补持久回执；不预建七套回执表，也不冒用同步 clientId/回执。

单纯设置某字段可以使用条件更新，不必一律再包一层公共回执。版本、墓碑、归属检查仍然适用，不能靠“看起来幂等”允许迟到重放覆盖后续编辑。

普通同步 PATCH 目前主要按 id＋owner 更新，owner 锁只保证提交顺序；工具端单独增加 expectedRevision，不能阻止之后到达的离线旧 PATCH。[sync-sql.builder.ts](D:/codeRepertory/MyCodeRepertory/omni-butler/apps/server/src/sync/sync-sql.builder.ts:259)。

因此不再要求七模块统一增加 revision/候选体系，但每项开放的写能力必须说清冲突语义：

- 普通元数据默认沿用现有同步行为，不承诺“全端不会覆盖”；这是保留现状，不把它包装成已解决的并发问题。
- 笔记、图片、AI 设置继续使用已有版本保护；派生值继续由业务规则维护。
- 对需要“不静默覆盖”的字段或操作，基线检查必须覆盖其在线写入和相关离线上传，并提供冲突后的重新读取/确认路径。只改该范围，不扩大为全库框架；未具备该保证时不宣称具备。

### 4.3 已有功能的边界

- 时间冲突收尾、待办两层/父子完成、进度满后确认、月底重复、会员自然日账期及事件撤销语义保持。
- 待办创建/新增最多 1000 步；已同步合并的超限结构可以保留或减少。future 删除只有主任务写停止标记，子任务操作不停止整个主任务系列。
- 笔记正文 20,000 字、最多 10 个有效标签、创建时间事实不可改、正文基线和删除墓碑继续校验。恢复当前会恢复所属版本/音频/图片，不区分删除批次，不借重构改产品语义。
- AI 整理任务成功与正式正文采用是两件事。只有准备开放“整理并保存”工具时，才补全服务器采用身份和跨端去重，防止客户端再追加一次；普通笔记 CRUD 不以此改造为前提。
- 新只读工具不偷偷触发日签初始化、重复待办物化、默认分类或计费。已有本机 watch 和设置 GET 的内部行为无需全面改写；适配器应按实际副作用提供准确能力说明。
- 物品/会员图片继续用 ImagesService；noteImage 的 businessId 是 note_images.id。已有附件回执、CAS、私有下载及垃圾清理继续复用。

## 6. 实施顺序与完成标准

以一个完整业务能力为单位推进，而不是先完成所有架构改造：

1. 选择该能力，确认当前行为与所需字段；有已有服务方法就复用，缺少才新增。
2. 补齐该能力的查询/写入、权限、事务、必要的重试和冲突处理，运行定向测试。
3. 将同一方法接入应用内工具调用和 MCP，验证相同参数得到一致结果；再扩展下一项能力。
4. 逐步覆盖第 3 节七模块的查询、新增、修改、删除及范围统计，再组合周/月总结。先读后写可作为每个模块的交付顺序，不是把最终目标缩为只读。

基础缺口按被触及的能力修复。没有实际需求时，不迁移自动续费调度、不拆 ASR/AI worker、不重写快照校验、不改全部客户端 Repository，也不预建所有方法的 HTTP API。

完成判断以用户能力为准：

| 目标 | 必须证明的结果 |
|---|---|
| 应用内对话助手 | 模型可提出工具调用，经服务端校验执行后收到真实结果；支持连续对话与结果卡片，冲突/确认不冒充成功 |
| Codex MCP | 获授权的 Codex 调用同一业务方法完成七模块 CRUD，结果能由应用现有同步链读到 |
| 周/月总结 | 任意合法日期范围的统计完整、口径明确、可核对；缺失或未同步数据如实说明；需要保存时能生成普通笔记 |
| 写入正确性 | 跨 owner 拒绝、事务不部分提交、重试不重复副作用、删除不被迟到请求复活；冲突行为与声明一致 |
| 改动范围 | 仅新增实际调用需要的方法、校验及入口；每个新类/表/任务都有具体用途和验证证据 |
