## 1. 编写范围

本文回答三个问题：当前系统实际使用了什么技术、这些技术在代码中承担什么职责、现阶段为什么保留这些选择。尚未进入代码、只存在于设想中的能力不列为当前技术栈。

主要事实来源如下：

- 客户端依赖与版本：`apps/client/pubspec.yaml`、`apps/client/pubspec.lock`
- 客户端入口、路由与本地数据：`apps/client/lib/main.dart`、`apps/client/lib/app/router/app_router.dart`、`apps/client/lib/core/database/app_database.dart`
- 同步实现：`apps/client/lib/core/sync/`、`apps/server/src/sync/`、`deploy/powersync/`
- 服务端依赖与模块：`apps/server/package.json`、`apps/server/src/app.module.ts`、`apps/server/prisma/schema.prisma`
- 部署与镜像：`apps/server/Dockerfile`、`deploy/docker-compose.yml`、`deploy/image-sync/`
- 发布流程：`.github/workflows/release-clients.yml`、`installer/windows/omni-butler.iss`

## 2. 当前系统定位与选型原则

从现有实现看，Omni Butler 是一个面向个人自托管场景的、本地优先的生活与效率管理应用，当前客户端目标平台是 Windows 和 Android。

技术选择围绕以下约束展开：

1. **离线可用。** 业务数据先落本机 SQLite；没有服务器或网络不可用时，核心业务仍能读写。
2. **显式同步。** 用户连接自托管服务后才启用远端同步；同步状态不能成为普通本地 CRUD 的前置条件。
3. **双端复用。** Windows 和 Android 共用 Dart 业务层、数据层和大部分 UI，平台差异集中在窗口、托盘、通知、存储空间等边界。
4. **个人部署优先。** 服务端保持模块化单体和单一内部数据归属，不引入当前规模用不到的微服务、缓存或消息队列。
5. **迁移可恢复。** 更换服务器、覆盖目标数据、进程中断恢复和幂等重试在代码中有专门的控制库、快照与回执机制。
6. **敏感信息分层存放。** 普通偏好、业务数据、设备会话凭证和服务端签名密钥分别存储，不将长期凭证写进业务表或仓库。

## 3. 总体技术架构

```text
Windows / Android Flutter 客户端
  ├─ Riverpod：依赖注入与状态编排
  ├─ GoRouter：七个一级路由
  ├─ Drift：类型安全查询、事务和本地迁移
  ├─ SQLite：本地业务事实状态与离线队列
  ├─ PowerSync SDK：结构化数据增量下行和本地变更队列
  ├─ Dio：认证、同步上传、迁移和图片 API
  └─ 系统能力：安全存储、本地通知、文件选择、Windows 窗口/托盘
                         │
                         ├─ HTTPS/HTTP → NestJS API
                         │                  ├─ 设备会话与 JWT/JWKS
                         │                  ├─ PowerSync CRUD 批量上传
                         │                  ├─ 数据源迁移协议
                         │                  └─ 图片代理与校验
                         │
                         └─ PowerSync 协议 → PowerSync Service
                                                │
                                    PostgreSQL 17（逻辑复制源）
                                                │
                         可选 MinIO（物品/会员图片私有对象）
```

结构化数据的上传和下行不是同一条链路：客户端本地事务由 PowerSync 形成 CRUD 队列，但上传由自定义连接器调用 NestJS 的 `/sync/operations`；服务端写入 PostgreSQL 后，再由 PowerSync Service 通过逻辑复制向设备下发变化。图片则完全绕开 PowerSync Schema，使用独立的认证 API 和对象存储。

## 5. 客户端技术选择与代码事实

### 5.1 Flutter 只覆盖 Windows 与 Android

仓库当前仅保留 `apps/client/windows/` 和 `apps/client/android/` 平台工程，没有 Web、iOS、macOS 或 Linux 平台工程。因此“跨平台”在当前项目中应准确理解为 Windows 与 Android 双端，而不是全平台承诺。

Flutter 的收益是业务模型、Repository、Riverpod Provider、路由和共享组件可以复用；平台特有代码仍然存在：

- Windows 使用 Flutter 同引擎多窗口能力、自定义 C++ 托盘控制器、`MethodChannel`、Win32/FFI 和窗口位置恢复。
- Android 使用紧凑布局与管理聚合导航，并通过平台通道读取可用存储空间。
- 本地通知同时配置 Windows 和 Android 实现。

UI 基于 Material 3 行为构建，但主题和控件外观集中在 `app/theme/` 与 `shared/ui/` 的语义 Token、`Omni*` 组件中，业务页面不直接形成多套独立设计系统。

### 5.2 Riverpod 与 GoRouter

Riverpod 不只承担页面状态，也用于组装数据库、认证仓库、同步运行时、通知服务和迁移协调器。启动时通过 `ProviderScope.overrides` 注入当前活动数据库与会话；数据源迁移完成后，以 generation 变化使依赖重新绑定到新运行时。

GoRouter 当前配置七个一级路径：

- `/home`
- `/todos`
- `/events`
- `/inventory`
- `/timeline`
- `/memberships`
- `/settings`

业务功能开关在路由层统一阻止进入已关闭模块；Android 紧凑宽度下，事件、物品、会员使用聚合管理布局。

### 5.3 Drift、SQLite 与本地优先

`AppDatabase` 当前 Schema 版本为 `14`，声明 13 张 Drift 表：待办、名言、每日名言、首页横幅、附件、分类、记录分类关联、事件、事件完成记录、物品、时间记录、会员、会员付款。

其中 11 张结构化业务表进入 PowerSync Raw Table Schema；以下数据有意留在设备侧或通过其他机制处理：

- `banner_settings`：首页横幅是本机内容，不同步到服务器。
- `attachments`：附件记录和本地文件路径属于设备；物品/会员主图的远端对象另走图片 API。
- `device_sync_metadata` 及图片传输状态表：属于同步运行时本机元数据，不作为业务表下行。
- `omni_butler_connection.sqlite`：独立控制库，保存活动数据库指针、会话键引用和迁移状态，不参与业务同步。

Drift 继续作为业务代码的类型安全访问层，PowerSync 则持有底层 SQLite 同步能力，两者通过 `drift_sqlite_async` 连接同一数据库。这使 Repository 无需为“纯本地”和“已连接服务器”维护两套实现，但也意味着 Drift、PowerSync 和桥接层版本是强耦合组合，升级时必须验证触发器、迁移和多设备行为。

### 5.4 数据源迁移与恢复

客户端不是简单替换服务器 URL，而是通过 `SyncConnectionCoordinator` 管理预检、候选数据库、快照、写入门禁、提交回执和崩溃恢复。迁移资产位于应用私有目录：

- 活动业务库初始为 `omni_butler.sqlite`。
- 连接控制库为 `omni_butler_connection.sqlite`。
- 迁移快照和候选库位于 `sync_migrations/<迁移ID>/`。

迁移时会暂停业务写入、通知协调和自动续费处理。服务端完整替换接口限制为最多 100000 条操作、32 MiB 请求数据，并使用最长 60 秒事务；迁移 ID、载荷摘要和回执共同保证重试不会重复替换数据。

### 5.5 本机配置与敏感数据

- SharedPreferences 存放主题、通知开关、功能开关等轻量设备配置。
- Flutter Secure Storage 存放设备会话凭证；控制库只保存安全存储键的引用。
- 业务图片复制到应用私有目录，离线时从本机缓存读取。
- UUID 用作业务记录、同步客户端和操作的稳定标识。

该分层避免把长期凭证写进普通 SQLite 业务表，也避免将设备私有文件路径同步到其他设备。

## 6. 同步技术选择与一致性策略

### 6.1 为什么使用 PowerSync

当前需求不是“在线 API CRUD”，而是本机可写、多设备最终同步。PowerSync 提供本地 SQLite、变更队列、逻辑复制下行和检查点能力，适合这个数据流。当前实现没有把上传完全交给通用后端，而是保留自定义 NestJS 写入层，以执行字段白名单、幂等、墓碑和业务一致性检查。

同步数据流如下：

1. Repository 通过 Drift 在本地 SQLite 中提交事务。
2. PowerSync Raw Table 触发器将本地变化写入 CRUD 队列。
3. `OmniPowerSyncConnector` 将同一本地事务整理为批量操作，请求 `/sync/operations`。
4. NestJS 在 PostgreSQL 单事务内校验并写入，保存幂等回执。
5. PowerSync Service 从 PostgreSQL 逻辑复制流读取变化。
6. `auth.user_id()` 对应的数据流下发到当前设备，本地 Drift 查询自动看到变化。

### 6.2 一致性保护

当前代码已有以下保护，而不是仅依赖“最后写入覆盖”：

- 服务端以表名和列名白名单限制通用写入。
- SQL 值参数化；表名、列名只从静态白名单生成。
- 客户端事务使用 `clientId + transactionId + payloadHash` 做幂等校验。
- 永久删除写入墓碑，阻止离线旧设备通过 PUT 恢复已删除记录。
- 父记录删除后，关联子记录和分类关联按规则处理。
- 每日名言对旧随机 ID 做同日期身份归并。
- 自动续费产生的会员数据在服务端做确定性归一和一致性检查。
- 数据源完整替换使用独立迁移回执，普通同步回执与迁移回执不混用。

### 6.3 当前同步边界

PowerSync 只同步结构化业务数据。它不传输图片二进制、不同步首页横幅、不同步普通设备偏好，也不承担用户注册或多租户账号管理。

## 7. 服务端技术选择与代码事实

### 7.1 NestJS 模块化单体

服务端当前由五个业务/基础模块组成：`PrismaModule`、`HealthModule`、`AuthModule`、`SyncModule`、`ImagesModule`。部署时它们运行在同一个 API 进程中。

保留模块化单体的原因是：现有部署面向个人服务器，业务量和团队边界都没有证明拆分微服务的收益；单体可以让同步事务、所有者替换、会话撤销和图片元数据更新保持在明确的数据库事务边界内。

NestJS 全局启用了：

- 固定 API 前缀 `/omni-butler/api/v1`
- 32 MiB JSON body 上限
- Helmet 安全响应头
- `ValidationPipe` 的字段白名单、未知字段拒绝和类型转换
- Swagger/OpenAPI 文档

### 7.2 Prisma 与受控 SQL 并存

Prisma 负责 Schema、生成的类型、常规数据访问和 `prisma migrate deploy`。API 容器启动时先执行正式迁移，再启动 NestJS。

同步上传需要对 11 张业务表接收统一 CRUD 结构，因此没有为每张表创建重复的传统 Controller/Service。`SyncSqlBuilder` 根据静态表/列白名单生成 SQL 结构，并将数据值作为参数提交。这里使用受控 SQL 是同步协议的特定实现，不代表项目放弃 Prisma，也不应扩展成任意 SQL 接口。

### 7.3 PostgreSQL 17

PostgreSQL 同时承担：

- 服务器端结构化业务数据事实状态
- 单一内部 `SyncOwner` 与设备会话
- 普通同步和完整迁移幂等回执
- 永久删除墓碑
- 图片元数据和对象清理队列
- PowerSync 逻辑复制数据源
- PowerSync 自身的 PostgreSQL bucket storage

Compose 显式启用 `wal_level=logical`，并配置复制槽和 WAL sender。业务库与 PowerSync 状态库是不同数据库，但位于同一个 PostgreSQL 服务和持久卷中。

### 7.4 设备会话，而非传统账号系统

当前服务没有注册、邮箱登录、密码找回、角色或用户管理。

认证事实如下：

- 部署者配置至少 16 字符的 `SYNC_SECRET`。
- 客户端以恒定时间摘要比较验证同步密钥。
- 验证成功后创建高熵设备凭证，数据库只保存 SHA-256 摘要。
- 设备会话固定有效 30 天；刷新不会延长到期时间，也不会轮换设备凭证。
- API Access Token 和 PowerSync JWT 最长有效 15 分钟。
- Access Token 每次请求还会检查设备会话，因此断开后可立即撤销 API 权限。
- JWT 使用 RS256；RSA 密钥首次启动自动生成并持久化，JWKS 供 PowerSync 验签。
- `SyncOwner` 只是单人部署的数据隔离标识，不是产品账号。

该方案适合当前个人自托管范围，但不能表述为已支持多用户、组织、权限模型或互联网开放注册。

### 7.5 图片同步：认证代理 + 私有 MinIO

图片同步由 `IMAGE_SYNC_ENABLED` 控制，默认关闭。开启后：

- MinIO 只在 Docker 内网暴露给 API，客户端不持有对象存储地址或凭证。
- NestJS 使用固定私有桶 `omni-butler-images`，通过 AWS S3 SDK 代理上传、下载和删除。
- 当前只接受物品图片与会员图片两类业务目标。
- 单张图片限制 20 MiB，服务端重新计算 SHA-256，并用 Sharp 完整解码。
- 支持 PNG、JPEG、WebP、GIF，输入像素数最多 4000 万。
- 图片元数据、显式清空标记和操作回执写入 PostgreSQL。
- 旧对象进入延迟清理队列，由 API 进程内定时任务回收。
- 首页横幅仍只保存在本机。

MinIO 是当前部署内置实现，端点和桶由服务端固定；代码没有向客户端或部署者开放外部 S3/COS 配置。因此不能把“S3 兼容”误写成当前已支持任意云对象存储。

## 8. 部署与网络选择

Docker Compose 是仓库当前唯一维护的完整服务端编排，包含：

- `postgres`：PostgreSQL 17、业务库、PowerSync storage 数据库和逻辑复制配置
- `api`：Node.js 24 上运行的 NestJS 服务，启动前执行 Prisma migration
- `powersync`：按镜像摘要固定的 PowerSync Service
- `minio`：图片同步开启时启动，关闭时缩为零副本并保留数据卷

持久化卷包括 PostgreSQL 数据、JWT 密钥、MinIO 凭证和图片对象。图片同步关闭后，图片与凭证卷仍保留，重新开启可继续使用。

Compose 本身不终止公网 TLS。仓库部署说明采用宿主机 Nginx 将固定 API 路径和 PowerSync 路径反向代理到容器端口：

- API：`/omni-butler/api/v1/`
- PowerSync：`/omni-butler/powersync/`

可信局域网可以显式使用 HTTP；公网或不可信网络必须在反向代理层使用 HTTPS/WSS。PostgreSQL 和 MinIO 不应直接暴露给客户端。

## 9. 测试、静态检查与发布

### 9.1 客户端

当前仓库包含 55 个 `*_test.dart` 测试文件，覆盖 Repository、数据库迁移、同步运行时、数据源迁移、图片同步、通知、响应式布局、Windows 窗口/托盘及 Golden UI 等。真实 PostgreSQL/PowerSync/MinIO 测试由显式 `dart-define` 开关启用，普通 `flutter test` 中跳过不能等同于真实链路已验证。

常用验证入口：

```powershell
cd apps/client
flutter analyze
flutter test
```

### 9.2 服务端

服务端使用 ESLint 9、typescript-eslint、Prettier、Jest、ts-jest 和 Supertest。TypeScript 开启 `strict`、`noImplicitOverride`、`noUncheckedIndexedAccess`；ESLint 强制显式函数返回类型并禁止未处理 Promise。

常用验证入口：

```powershell
cd apps/server
npm ci
npm run build
npm run lint
npm test
```

真实 PostgreSQL 集成测试需要指向名称以 `_test` 或 `_integration` 结尾的隔离数据库，不能对日常部署数据库运行清理型测试。

### 9.3 客户端发布流水线

推送 `v*.*.*` 标签时，GitHub Actions 会核对标签与 `pubspec.yaml` 的 build name，并执行客户端静态分析与稳定冒烟测试。随后分别生成：

- 签名 Android APK
- 签名 Android AAB
- Windows x64 便携 ZIP
- Windows x64 Inno Setup 用户级安装包
- `SHA256SUMS.txt`

当前流水线只发布客户端，不构建或部署生产服务器；服务端仍通过部署目录中的 Docker Compose 在目标服务器更新。

## 10. 当前明确不采用或尚未支持的技术

| 技术或方案 | 当前结论 | 代码事实 |
|---|---|---|
| 微服务 | 不采用 | 所有 API 模块运行在一个 NestJS 进程中 |
| Redis | 不采用 | 无缓存、分布式锁或共享会话实现 |
| RabbitMQ/Kafka | 不采用 | 图片回收使用进程内定时任务和 PostgreSQL 队列表 |
| 传统用户注册/邮箱登录/RBAC | 不支持 | 当前为部署密钥 + 单一内部 owner + 设备会话 |
| Web、iOS、macOS、Linux 客户端 | 尚未支持 | 仓库仅有 Windows 与 Android 平台工程 |
| 外部 S3/COS 可配置接入 | 尚未支持 | MinIO 内网端点和私有桶在服务端固定 |
| 将图片二进制放入 PowerSync | 不采用 | 图片使用独立 API、PostgreSQL 元数据和 MinIO 对象 |
| 第三方网盘复制 SQLite/WAL | 不采用 | 当前同步以 PowerSync 协议和服务端事务为边界 |
| 独立后台管理端 | 尚未实现 | 仓库没有管理前端或管理 API 模块 |
| 服务端自动发布 | 尚未实现 | GitHub Actions 仅构建并发布客户端 |

## 11. 选型维护规则

1. 依赖版本以 lock 文件和固定镜像摘要为准，README 中的版本说明必须与之同步。
2. 新增技术前先确认它解决的是现有代码中的真实问题，而不是为可能出现的规模提前增加复杂度。
3. 修改 Drift Schema、PowerSync Raw Table、服务端 Prisma Schema 或同步白名单时，四者必须作为同一项变更审查。
4. 调整认证或数据源迁移协议时，必须同时验证丢响应重试、幂等、会话撤销、崩溃恢复和旧设备行为。
5. 开启或修改图片同步时，必须同时验证 PostgreSQL 元数据、MinIO 对象、凭证卷和本机缓存，不能只验证上传接口成功。
6. 文档不得把普通测试中的条件跳过、成功构建或 CI 产物生成写成真机与生产环境已验收。
