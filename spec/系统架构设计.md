# Omni Butler 系统架构设计

## 1. 架构范围

本文只描述仓库当前实际采用的架构。产品目标见 `需求书.md`，已实现能力见 `第一版桌面端当前交付说明.md`，所有未完成事项见 `剩余功能与验收清单.md`。

当前系统是面向个人使用的本地优先应用：Windows/Android 客户端可完全离线使用；用户在设置中显式开启同步后，结构化数据才连接个人自托管的 NestJS、PostgreSQL 与 PowerSync。

## 2. 总体结构

```text
Flutter 客户端
├─ Presentation：页面、共享 Omni* 组件、响应式壳层
├─ Riverpod：依赖与页面状态编排
├─ Repository：业务规则与本地 CRUD
├─ Drift：类型安全数据访问
├─ PowerSync：可选的结构化数据同步与 CRUD 队列
├─ SQLite：本地事实状态
└─ 应用私有目录：原图与已验证图片缓存
          │
          │ 开启同步后：HTTPS REST + PowerSync 协议
          ▼
NestJS API
├─ AuthModule：同步密钥、设备会话、JWT/JWKS
├─ SyncModule：白名单批量写入、连接预检与服务器迁移
├─ ImagesModule：物品/会员图片清单、上传、下载与对象回收
├─ PrismaModule：PostgreSQL 访问与生命周期
└─ HealthModule：服务与数据库健康检查
          │
          ├────────► PostgreSQL：结构化数据、迁移回执与图片元数据
          ├────────► PowerSync：逻辑复制、bucket storage、增量下发
          └────────► MinIO（可选）：私有物品/会员图片对象
```

## 3. 客户端架构

### 3.1 目录职责

| 目录 | 职责 |
|---|---|
| `apps/client/lib/app/` | 根应用、GoRouter、主题、响应式 Token |
| `apps/client/lib/core/database/` | Drift Schema、迁移和数据库生命周期 |
| `apps/client/lib/core/sync/` | PowerSync Schema、连接器、运行时、数据源迁移和图片同步协调 |
| `apps/client/lib/core/auth/` | 自托管服务器设备会话，不是用户账号体系 |
| `apps/client/lib/core/notifications/` | 通知偏好、计划生成和原生通知 |
| `apps/client/lib/core/attachments/` | 本机图片记录、私有文件管理和可恢复图片传输队列 |
| `apps/client/lib/features/` | 首页、待办、事件、物品、时间、会员、设置 |
| `apps/client/lib/shared/` | 通用 UI、搜索、分类标签和布局能力 |

Presentation 不直接拼接 SQL、保存 Token 或调用 PowerSync CRUD 队列；业务数据操作经过 Repository。共享视觉行为优先落在 `Omni*` 组件，不在页面重复实现。

### 3.2 本地数据库

- 默认使用 Drift 管理的 SQLite，本地模式不依赖服务器。
- 业务记录使用客户端生成的 UUID v7，可离线创建。
- 开启同步后，PowerSync 与 Drift 通过 `drift_sqlite_async` 访问同一 SQLite 文件。
- 待办表通过可空 `parent_id` 建立两级自关联；进行中查询以未完成状态为边界，完成历史以 `completed_at` 为时间边界，计划日期不再决定未完成任务的可见性。
- PowerSync Raw Table 变更触发器把本地业务写入变成上传队列；Drift 继续提供类型安全查询。
- 软删除字段 `deleted_at` 参与同步；回收站负责恢复、永久删除和 30 天清理。
- 本机附件表、文件路径和图片传输队列不进入 PowerSync Schema；物品/会员图片通过认证 API 单独同步，首页横幅保持本机。

### 3.3 路由与响应式布局

GoRouter 当前提供 `/home`、`/todos`、`/events`、`/inventory`、`/timeline`、`/memberships`、`/settings` 七个一级路由。

- 移动平台 `<720`：底部五入口。
- 桌面平台 `<1200`：58px 紧凑导航轨，保持桌面骨架。
- 桌面平台 `>=1200`：192px 展开侧栏。
- 单一飞书蓝语义主题支持跟随系统、浅色和深色。

## 4. 同步架构

### 4.1 当前边界

同步默认关闭，用户只需填写服务器 IP 地址（或域名）、端口与部署者设置的同步密钥，固定接口路径由客户端内部拼接。系统不提供注册、邮箱登录、用户管理或账号切换。

当前通过 PowerSync 同步以下结构化表：待办、名言、每日名言选择、分类、标签关联、事件、事件完成历史、物品、时间记录、会员和会员支付历史。

服务器设置 `IMAGE_SYNC_ENABLED=true` 后，物品和会员主图通过认证 API 与内置 MinIO 同步；图片二进制、图片同步清单和本机缓存路径不进入 PowerSync。

以下内容始终不同步：首页横幅、本机应用偏好、迁移控制库和本机缓存路径。

### 4.2 设备会话

1. 客户端向 `POST /omni-butler/api/v1/auth/connect` 提交同步密钥和预检得到的服务器身份。
2. NestJS 校验部署级 `SYNC_SECRET`，签发最长 15 分钟的 Access Token 与固定期限、不轮换的高熵设备凭证。
3. 客户端通过 `POST /omni-butler/api/v1/auth/powersync-token` 获取 PowerSync 专用 JWT。
4. PowerSync 使用 NestJS 暴露的 JWKS 校验令牌。
5. Access Token 过期后使用同一设备凭证刷新；刷新不延长设备会话固定期限。
6. 断开连接时删除当前设备会话；用户可选择保留或清除结构化同步数据。

数据库中的内部所有者只用于兼容现有 `user_id` 关系，不是可登录账号，也不暴露到产品界面。

### 4.3 上传与下行

```text
本地 Repository 写入
  → Drift/SQLite 提交
  → PowerSync 捕获 CRUD
  → OmniPowerSyncConnector 批量提交 /sync/operations
  → NestJS 校验表与字段白名单，并强制注入当前内部所有者
  → PostgreSQL 事务落库
  → PowerSync 通过逻辑复制读取变化
  → 同一所有者的其他设备增量下载
```

本地保存成功与云端同步成功必须分别表达。同步失败不能回滚已经成功写入的本地业务数据。

### 4.4 数据边界与冲突

- 服务端不接受客户端指定目标 `user_id`，由认证上下文强制注入。
- 上传使用表、操作类型和字段三层白名单，并使用参数化 SQL。
- 当前删除采用软删除；从属历史与标签关联按 Repository/数据库规则处理。
- 当前并发冲突仍依赖 PowerSync 下行和服务端写入顺序；冲突审计与人工处理属于未完成项，不应在界面宣称已解决。

## 5. 服务端架构

服务端是 NestJS 模块化单体，使用 Prisma 访问 PostgreSQL。运行时注册 `AuthModule`、`SyncModule`、`ImagesModule`、`PrismaModule` 和 `HealthModule`。

主要接口：

| 接口 | 作用 |
|---|---|
| `POST /omni-butler/api/v1/auth/connect` | 使用同步密钥建立固定期限设备会话 |
| `POST /omni-butler/api/v1/auth/refresh` | 使用稳定设备凭证刷新 Access Token |
| `POST /omni-butler/api/v1/auth/disconnect` | 删除当前设备会话 |
| `POST /omni-butler/api/v1/auth/powersync-token` | 获取 PowerSync 专用凭证 |
| `GET /omni-butler/api/v1/auth/jwks` | 向 PowerSync 提供公钥 |
| `POST /omni-butler/api/v1/sync/operations` | 幂等批量写入 PowerSync CRUD |
| `POST /omni-butler/api/v1/sync/connection-preview` | 只读预检目标数据源 |
| `POST /omni-butler/api/v1/sync/migrations` | 原子替换目标服务器快照 |
| `POST /omni-butler/api/v1/sync/migrations/status` | 查询持久迁移回执 |
| `/omni-butler/api/v1/images/*` | 图片能力、清单、上传、下载与清空 |
| `GET /omni-butler/api/v1/health` | API 与数据库健康检查 |

## 6. 部署架构

`deploy/docker-compose.yml` 当前编排：

- PostgreSQL 17，启用逻辑复制，使用持久化数据卷。
- NestJS API，启动时执行 Prisma migration；PowerSync publication 由 migration 创建。
- 固定镜像摘要的 PowerSync Service，使用 PostgreSQL 作为 bucket storage。
- 可选的固定版本 MinIO，只在 Docker 内网提供物品/会员图片存储，数据与随机凭证分别使用持久卷。

PostgreSQL 与 MinIO 端口默认不映射到宿主机。可信局域网可在明确知情时使用 HTTP；公网部署必须通过 HTTPS/WSS 反向代理。同步密钥由环境变量提供；RSA 私钥由 API 自动生成并保存在持久卷，MinIO 凭证由启动脚本生成并保存在独立凭证卷。

## 7. 技术约束

- 不把 SQLite/WAL 文件直接放入网盘或第三方同步盘。
- 不在客户端内置数据库密码、同步密钥、RSA 私钥或对象存储永久密钥。
- 不把图片字段加入当前 PowerSync Schema。
- 不因桌面窗口变窄而切换为移动端导航。
- SDK、数据库 Schema 或 PowerSync 镜像升级后，必须重新验证真实双设备同步。
- 备份恢复、冲突处理、真机矩阵、发布签名和生产运维状态统一见 `剩余功能与验收清单.md`。
